# تحديث الصفحة المنشورة - تصميم التنفيذ

## الهدف

تحديث النسخة المنشورة من صفحة `داري الحنونة` بالتعديلات المعتمدة الموجودة محلياً، مع التحقق أولاً من إعداد GitHub Pages الحقيقي قبل أي دفع أو نشر فعلي.

## السياق الحالي

- المشروع صفحة ثابتة تعتمد على `index.html`.
- ملف `README.md` يذكر أن النشر يتم عبر GitHub Pages.
- المستودع مرتبط بـ GitHub عبر `origin`.
- الفرع الحالي هو `main`.
- لا توجد GitHub Actions خاصة بالنشر داخل `.github/workflows`.
- لا يوجد `CNAME` داخل المشروع.
- هذا يرجح أن النشر يتم من `main`/root، لكن لا يكفي للاعتماد عليه دون تحقق من إعداد Pages الفعلي في GitHub.

## المشكلة

لدينا نسخة محلية محدثة ومختبرة، لكن لا ينبغي دفعها مباشرة إلى الإنتاج قبل معرفة:

1. مصدر GitHub Pages الفعلي.
2. هل النشر يتم من `main`/root أو من مسار/فرع آخر.
3. ما الملفات التي يجب أن تبقى في المستودع، وما الذي لا ينبغي إدخاله في تحديث النشر.

## البدائل المدروسة

### البديل 1: تحقق ثم نشر مباشر

التحقق من إعداد GitHub Pages أولاً، ثم إذا ثبت أن المصدر هو `main`/root يتم تجهيز المحتوى النهائي ودفعه مباشرة.

**الإيجابيات**
- أسرع مسار إلى الإنتاج.
- أقل تعقيد تشغيلي.
- مناسب لمشروع static بسيط.

**السلبيات**
- يحتاج انضباطاً في تنظيف الملفات قبل الدفع.
- أي خطأ في تحديد مصدر النشر قد يسبب دفعاً غير مفيد.

### البديل 2: تحقق ثم فرع و PR

التحقق أولاً، ثم وضع التعديلات في فرع جديد وفتح Pull Request قبل الدمج.

**الإيجابيات**
- أكثر تحفظاً.
- أسهل في المراجعة قبل النشر.

**السلبيات**
- أبطأ.
- يضيف خطوة تشغيلية ليست ضرورية غالباً في مشروع static صغير إذا كانت إعدادات Pages واضحة.

### البديل 3: إعادة بناء آلية النشر

إذا ظهر أن GitHub Pages لا يعتمد `main`/root أو أن الإعدادات الحالية غير سليمة، تتم إعادة تصميم مسار النشر.

**الإيجابيات**
- يعالج أي انحراف جذري في البنية.

**السلبيات**
- خارج نطاق الحاجة الحالية إن كانت إعدادات Pages سليمة.
- يزيد التعقيد بلا داعٍ.

## القرار المعتمد

اعتماد **البديل 1**:

1. التحقق من إعداد GitHub Pages الحقيقي أولاً.
2. إذا كان المصدر هو `main`/root، يتم تجهيز تحديث نظيف ودفعه مباشرة.
3. إذا لم يكن كذلك، يتم إيقاف التنفيذ وإعادة تصميم مسار النشر بناءً على الواقع الفعلي.

## حدود التنفيذ

### ضمن النطاق

- التحقق من إعداد GitHub Pages.
- تحديد الملفات المطلوبة للنشر الفعلي.
- إزالة أو استبعاد الملفات التطويرية غير اللازمة من عملية التحديث.
- تحديث النسخة المنشورة وفق إعداد Pages الصحيح.

### خارج النطاق

- إعادة هيكلة شاملة للمشروع.
- تغيير مزود الاستضافة.
- إدخال pipeline نشر جديدة إلا إذا أثبت التحقق أن المسار الحالي غير صالح.

## بنية التنفيذ المقترحة

### المرحلة 1: التحقق

- فحص إعداد GitHub Pages الفعلي للمستودع.
- تأكيد الفرع والمسار المنشورين فعلياً.

### المرحلة 2: فرز الملفات

- إبقاء الملفات اللازمة لتشغيل الصفحة.
- التعامل بحذر مع الملفات التالية قبل النشر:
  - `node_modules/`
  - `test-results/`
  - ملفات وتقارير التطوير المؤقتة
- تحديد ما إذا كانت ملفات الاختبار والإعداد (`tests/`, `package.json`, `playwright.config.ts`) ستبقى في المستودع أم سيتم فقط تجاهلها من منظور النشر العملي.

### المرحلة 3: النشر

- إذا كان Pages ينشر من `main`/root:
  - تجهيز الحالة النهائية المطلوبة.
  - تنفيذ الدفع إلى الفرع المعتمد.
- إذا كان Pages لا ينشر من `main`/root:
  - إيقاف التنفيذ.
  - توثيق الإعداد الفعلي.
  - تصميم خطة نشر مصححة قبل المتابعة.

## إدارة المخاطر

### خطر تحديد مصدر نشر خاطئ

يتم منعه بعدم الدفع قبل التحقق من إعداد GitHub Pages عبر المصدر الحقيقي.

### خطر دفع ملفات تطويرية غير لازمة

يتم احتواؤه عبر مرحلة فرز صريحة قبل النشر.

### خطر الاعتقاد أن أي push إلى `main` سيحدث الصفحة

لن يتم افتراض ذلك. سيتم اعتباره صحيحاً فقط إذا أكدته إعدادات GitHub Pages.

## التحقق بعد التنفيذ

- التأكد من نجاح الدفع إلى المصدر الصحيح.
- فتح الصفحة المنشورة والتحقق من ظهور التعديلات المعتمدة.
- التأكد من أن أهم العناصر الحرجة لا تزال سليمة:
  - الروابط الأساسية
  - نموذج التواصل
  - زر واتساب
  - التصميم المتجاوب الأساسي

## معايير النجاح

- معرفة إعداد GitHub Pages الحقيقي بدون تخمين.
- تحديث الصفحة المنشورة عبر المسار الصحيح فقط.
- عدم إدخال ملفات تطويرية غير لازمة إلى مسار النشر النهائي.
- بقاء الصفحة المنشورة مطابقة للتعديلات المحلية المعتمدة.
