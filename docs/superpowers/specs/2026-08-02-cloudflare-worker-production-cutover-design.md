# تفعيل Cloudflare Worker للإنتاج - تصميم التنفيذ

## الهدف

تفعيل مسار `Cloudflare Worker` إنتاجياً لمعرض الصور بحيث تُنقل جميع عمليات الكتابة إلى GitHub من المتصفح إلى الـ Worker، مع ربط الواجهة بعنوان الـ Worker الحقيقي حتى لا يحتاج المشرف إلى `GitHub PAT` داخل المتصفح عند تشغيل وضع Worker.

## الوضع الحالي

- المشروع الحالي موجود فعلياً في `/workspace`.
- ملف الـ Worker موجود في:
  - `cloudflare/worker.mjs`
  - `cloudflare/wrangler.toml`
  - `cloudflare/README.md`
- الواجهة في `index.html` تدعم مسار Worker وتحتوي على:
  - `DEFAULT_WORKER_API_BASE`
  - `callWorkerApi()`
  - `validateWorkerService()`
  - `loginWithWorker()`
- الاختبارات الحالية تغطي منطق Worker وبعض سيناريوهات الواجهة المرتبطة به.
- `Cloudflare MCP` غير ظاهر ضمن الخوادم المتاحة في هذه الجلسة، لذا مسار النشر الفعلي سيكون عبر `Wrangler CLI` إذا كان الاعتماد والأسرار متاحة.

## المشكلة

الحل البرمجي شبه مكتمل، لكن التفعيل الإنتاجي لم يُحسم بعد لأن:

1. `DEFAULT_WORKER_API_BASE` ما يزال فارغاً.
2. لا يوجد تأكيد بعد على نشر الـ Worker بعنوان فعلي قابل للاستخدام.
3. يلزم التأكد أن الواجهة تعمل إنتاجياً عبر الـ Worker دون الحاجة إلى `GitHub PAT` في المتصفح.
4. يلزم تشغيل اختبارات ما بعد الربط ثم دفع أي تغييرات لازمة إلى `main`.

## البدائل المدروسة

### البديل 1: Full Worker Cutover

ربط الواجهة مباشرة بعنوان الـ Worker الحقيقي بعد نشره، مع إبقاء مسار `GitHub PAT` كخطة احتياط داخلية فقط.

**الإيجابيات**
- يحقق الهدف التجاري والأمني مباشرة.
- يستفيد من العمل المنجز فعلاً دون إعادة تصميم.
- يقلل تعرض أسرار GitHub في المتصفح.

**السلبيات**
- يعتمد على توفر اعتماد Cloudflare والأسرار في الجلسة الحالية.

### البديل 2: Hybrid Soft Rollout

الإبقاء على التفعيل اليدوي عبر `localStorage` أو الإعدادات، دون ضبط القيمة الافتراضية في الواجهة.

**الإيجابيات**
- أقل مخاطرة أثناء الإطلاق.

**السلبيات**
- لا يحقق "الحل الحاسم" المطلوب.
- يبقي التفعيل الإنتاجي ناقصاً أو معتمداً على خطوة يدوية.

### البديل 3: الإبقاء على GitHub Direct فقط

تحسين المسار الحالي المعتمد على المتصفح و`GitHub PAT`.

**الإيجابيات**
- لا يحتاج بنية نشر إضافية.

**السلبيات**
- يخالف معيار النجاح الأساسي.
- يُبقي السر الحساس على جهة العميل.

## القرار المعتمد

اعتماد **البديل 1: Full Worker Cutover**.

## التصميم المعماري

### طبقة الكتابة

- يظل `gallery.json` هو المصدر العام المقروء من الواجهة.
- جميع عمليات الإدارة التي تغيّر `gallery.json` تمر عبر `POST /api/gallery/manifest` في الـ Worker.
- الـ Worker وحده يحتفظ بـ `GITHUB_TOKEN` ويتحدث مع GitHub Contents API.

### طبقة المصادقة

- تسجّل الواجهة دخول المشرف عبر `POST /api/auth/login`.
- يُعيد الـ Worker جلسة قصيرة العمر موقعة بـ `SESSION_SECRET`.
- تُرسل الجلسة في ترويسة `Authorization: Bearer <token>` عند عمليات الحفظ.

### تفعيل الواجهة

- تُحدّث `DEFAULT_WORKER_API_BASE` في `index.html` إلى رابط الـ Worker الحقيقي.
- عندما تكون هذه القيمة مضبوطة، يصبح Worker هو المسار الافتراضي الفعلي.
- يبقى fallback الداخلي في الكود لتقليل خطر الانكسار، لكنه لا يكون مطلوباً في المسار الإنتاجي الطبيعي.

## خطة التنفيذ

1. مراجعة ملفّات Worker والواجهة والاختبارات للتأكد من عدم وجود نواقص تشغيلية.
2. التحقق من توفر `Wrangler CLI` واعتماد Cloudflare في الجلسة.
3. التحقق من الأسرار المطلوبة أو طلب المفقود منها مرة واحدة فقط إذا تعذر الوصول إليه تلقائياً:
   - `GITHUB_TOKEN`
   - `ADMIN_SECRET`
   - `SESSION_SECRET`
4. نشر الـ Worker فعلياً عبر `Wrangler CLI`.
5. التقاط رابط الـ Worker النهائي.
6. تحديث `DEFAULT_WORKER_API_BASE` في `index.html`.
7. تشغيل اختبارات Worker والواجهة بعد التعديل.
8. دفع التغييرات إلى `main`.
9. التحقق من الموقع المنشور والـ Worker endpoint إنتاجياً.

## معالجة الأخطاء والمخاطر

### غياب Cloudflare MCP

لن يوقف التنفيذ بحد ذاته، لأن مسار النشر سيعتمد على `Wrangler CLI`.

### غياب اعتماد Cloudflare أو الأسرار

إذا تعذر النشر بسبب اعتماد أو سر غير متاح، سيتوقف التنفيذ عند هذه النقطة فقط مع طلب محدد ووحيد للقيمة أو الاعتماد الناقص.

### فشل التحقق بعد النشر

إذا نُشر الـ Worker لكن فشل `health` أو فشل الربط في الواجهة، تُعالج الأسباب أولاً ثم تُعاد الاختبارات قبل الدفع.

## الاختبارات والتحقق

- تشغيل اختبارات Node الخاصة بالـ Worker.
- تشغيل اختبارات Playwright المستهدفة لمسار Worker والواجهة.
- التحقق من أن تبويب الإعدادات يعرض حالة Worker بدلاً من مطالبة المسار الإنتاجي بمفتاح GitHub.
- التحقق من أن `DEFAULT_WORKER_API_BASE` يشير إلى رابط حقيقي عامل.
- التحقق من أن الموقع المنشور يستخدم الـ Worker دون الحاجة إلى `GitHub PAT` في المتصفح.

## حدود التنفيذ

### ضمن النطاق

- تفعيل Worker إنتاجياً.
- ربط الواجهة بعنوانه الحقيقي.
- أي تعديلات ناقصة مطلوبة لإكمال المسار.
- تشغيل الاختبارات.
- دفع التغييرات إلى `main`.

### خارج النطاق

- إعادة تصميم كاملة للوحة الإدارة.
- تغيير مزود النشر للواجهة من GitHub Pages.
- إضافة ميزات جديدة غير لازمة لتفعيل المسار الإنتاجي الحالي.

## معايير النجاح

- الـ Worker منشور فعلياً بعنوان عام حقيقي.
- `DEFAULT_WORKER_API_BASE` محدث في `index.html`.
- تشغيل الإدارة عبر Worker لا يتطلب `GitHub PAT` داخل المتصفح.
- الاختبارات اللازمة ناجحة.
- التغييرات مدفوعة إلى `main`.
